# Moras 竞品分析

把“看起来像什么”转成可验证的产品模型。结论必须区分事实、推断和待验证假设，并把每一项观察落到用户任务、系统能力、数据流或商业结果上。

## 工作流

1. **定义范围**：写清目标用户、平台/地区、竞品集合、研究日期、要回答的决策问题。不要把“做一个类似产品”当成足够的范围。
2. **收集证据**：优先使用官方产品页、定价/条款、用户提供的截图或可重复的公开操作。登录后页面、私有数据和手机上的其他内容不能被默认读取或外传。
3. **标注置信度**：
   - `[F]` 事实：页面文字、可见控件、截图明确呈现的内容。
   - `[I]` 推断：由多个事实合理推导的机制，说明推导链。
   - `[H]` 假设：需要实际注册、埋点、接口或用户访谈验证。
4. **重建闭环**：按“触达/注册 → 连接店铺 → 选品 → 创意/脚本 → 生成 → 合规 → 发布 → 观看/点击/成交 → 复盘/再创作”画出主流程。每一步写输入、输出、失败状态和下一步触发。
5. **建立矩阵**：比较 JTBD、核心能力、平台集成、AI 自动化深度、内容资产、数据指标、商业模式、权限/合规、迁移成本和可替代性。不要只罗列功能名称。
6. **形成判断**：分别输出“应复制的机制”“应改进的体验”“不应复制的风险”“需要先验证的未知”。机会按用户价值、收入潜力、实现成本、平台风险四项评分（1-5），说明评分依据。

## Moras 专项观察框架

- **产品定位**：是选品、内容生产、联盟营销、店铺运营，还是全链路协作；用一句 JTBD 定义，而不是复述品牌口号。
- **AI 专家编排**：记录每个专家的输入/输出和交接关系。Moras 公开页把 11 个专家分为 Product Research、Video Creation、Publish & Improve 三阶段；这属于 `[F]`，但专家是否独立模型、是否可单独调用属于 `[H]`。
- **移动端信息架构**：记录首屏任务、主导航、空状态、额度、连接状态、内容审核、发布动作和分析指标。特别检查“发现 → 创建”的跳转是否带上商品上下文。
- **选品可解释性**：记录评分字段、时间窗口、数据刷新、佣金/收益估算和“为什么推荐”解释。不要把站点宣传的预测收益当成实际保证。
- **内容闭环**：记录产品链接、脚本、语音、字幕、视频、标签、发布时间和归因 ID 是否保持关联。
- **商业模式**：区分订阅、额度、佣金分成、增值资产和平台服务费；把已公开的价格/分成与营销文案中的“可能变化”一起记录。

## 输出格式

按以下顺序组织报告：

1. 结论摘要（目标用户、核心循环、最大优势、最大风险）。
2. 证据边界（来源、日期、`[F]/[I]/[H]` 清单）。
3. 用户旅程与功能逻辑（主流程 + 异常流程）。
4. 能力矩阵（目标产品、Moras、直接竞品、替代方案）。
5. 商业模式与单位经济假设。
6. 移动端体验评估（信息架构、交互、状态、可访问性）。
7. 数据与平台依赖（事件、归因、TikTok 权限、内容/隐私风险）。
8. 机会排序、MVP 建议和验证实验。

需要表格字段或评分模板时，读取 [analysis-template.md](references/analysis-template.md)。

## 研究纪律

- 不复制 Moras 的品牌、文案、视觉资产或源代码；只抽象可迁移的机制。
- 不把宣传数字当作经审计结果；标明“官网宣称”并建议验证口径。
- 不进行绕过登录、验证码、付费墙或平台权限的抓取。
- 任何涉及发布、上传、授权店铺或传输用户资料的动作都必须停在分析层，除非用户另行明确授权。
