# Muses：四周路线图与内测方案

版本：V0.2

日期：2026-08-23

产品代号：Muses

内测规模：3–5 名自有商品商家

## 1. 四周目标

四周不是为了完成一个功能庞大的跨平台营销系统，而是为了回答一个商业问题：

> 小商家是否愿意持续使用 Muses 把 SKU 转成小红书内容，并实际发布？

四周结束时应获得：

- 一条用户可以独立完成的 SKU 到内容保存链路。
- 真实发布数量和发布阻力。
- 图片/动态的商品失真问题分布。
- iOS Live Photo 的真实发布结果，以及是否值得投入 Android Motion Photo 的决策证据。
- 单个被采用并发布内容包的真实模型成本。
- 用户对订阅、额度和继续使用的初步意愿。

## 2. 北极星与阶段指标

### 2.1 北极星指标

> 每名周活内测用户每周实际发布的小红书 SKU 内容包数量。

Demo阶段不自动埋点，通过一对一回访、帖子链接或用户展示的发布记录人工确认。

### 2.2 漏斗

| 阶段 | 手工口径 | 目的 |
|---|---|---|
| SKU开始 | 用户进入并开始上传图片 | 判断触发意愿 |
| SKU确认 | 商品事实和授权确认完成 | 判断表单阻力 |
| 图片成功 | 得到可审核图片 | 判断技术可用性 |
| 图片通过 | 用户确认商品没有明显失真 | 判断图片质量 |
| 动态成功 | 得到可审核AI动态 | 判断动态可用性 |
| 动态通过 | 用户确认动态没有明显失真 | 判断视频质量 |
| 内容保存 | 媒体和文案保存成功 | 判断初步采用 |
| 实际发布 | 用户提供帖子链接或当面确认 | 判断真实价值 |
| 再次创作 | 7天内创建新SKU或新版本 | 判断留存价值 |

### 2.3 建议观察门槛

样本仅3–5人，不用统计显著性或虚假精确百分比做最终市场结论。以下是方向性门槛：

- 至少 3 名用户完整完成一次任务。
- 至少 2 名用户实际发布。
- 至少 2 名用户在 7 天内再次使用。
- 大多数已保存内容来自通过审核的首图或一次返修，而不是多次抽卡。
- 商品关键特征错误能够被用户发现并通过返修约束改善。
- 单个实际发布内容包的平均可变成本有机会被未来月费和额度覆盖。

若未达到，不直接判定模型或市场失败；先定位是流程、内容质量、格式兼容、发布意愿还是目标用户问题。

## 3. 四周路线图

### 第0阶段：2–3个工作日真实Demo

交付：

- 原生 SwiftUI iOS 17+ 工程。
- 本地 JSON 供应商配置。
- 临时 Key 和固定 Endpoint。
- SKU 输入、AI预填、商品确认。
- 一张图片、一段AI动态、一套小红书文案。
- 图片与动态人工审核。
- iOS Live Photo、静态图和 MP4 保底。
- 保存、复制和本地历史。

决策门：

- 如果 iOS 全链路不通，不进入外部内测，先修复。
- Android 客户端不属于 Demo；Android 用户不进入本轮 App 内测名单。
- 如果供应商接口无法支持稳定参考图或任务恢复，先收窄或调整适配器，不增加功能。

### 第1周：打通与内部验证

目标：连续运行，不丢任务、不重复扣费、不把失真内容当成完成。

工作项：

- 修复真实接口字段、超时和轮询状态差异。
- 完善本地任务持久化和App恢复。
- 检查图片/视频文件下载、MIME和大小。
- 形成首个水杯类商品的标准提示词模板。
- 使用至少2个不同SKU检查模板是否过拟合水杯。
- iPhone连续执行3次完整链路。
- 记录 iPhone 发布 Live Photo 后在 Android 小红书客户端的观看表现；这不代表 Android 上传能力。
- 将所有失败原因结构化。

周末输出：

- 内部测试记录。
- 已知问题清单。
- 单任务耗时和成本。
- 可交付给用户的内测说明。

### 第2周：3–5名 iPhone 用户受控内测

目标：观察用户是否能在不口头指导的情况下完成任务。

工作项：

- 每名用户发放独立、限额、短期 Key。
- 用户第一次操作时只观察，不替用户点击。
- 记录卡住位置、错误理解和放弃原因。
- 每位用户最多3个SKU。
- 每个SKU默认1张图和1次AI动态。
- 出现模型失败时人工判断是否补发额度。
- 每次任务后进行5分钟即时访谈。

重点验证：

- 3–6张图是否让用户觉得麻烦。
- AI预填是否减少填写量，还是引入更多纠错。
- 用户是否理解“审核”而不是无脑点击通过。
- 3–5秒动态是否真正增加发布意愿。
- 文案是否需要重写，哪类表达最不自然。
- iPhone 用户在 Live Photo 封装失败时是否接受 MP4 降级。

### 第3周：修复高频阻力、加入稳定实况并决策 Android Spike

目标：只修复阻碍实际发布的前三类问题。

优先级规则：

1. 会导致商品失真或误导的问题。
2. 会导致任务/费用丢失的问题。
3. 会阻止保存和发布的问题。
4. 多名用户反复遇到的表单与文案问题。
5. 视觉美化和低频偏好最后处理。

候选改进：

- AI预填摘要和错误字段快速修改。
- 审核失败原因一键带入提示词。
- 生成失败与下载失败分离重试。
- 确定性“稳定实况”模式：轻推拉/景深，降低成本和商品形变。
- 小红书语气选择：真实分享、干货测评、生活方式、好物推荐。
- 若 Android Motion Photo Spike 通过，再形成目标设备认证提示草案。
- 仅在 iOS 发布与复用反馈成立后，执行 Android Motion Photo 格式 Spike；Spike 不等于交付 Android App。

不在本周加入：自动发布、抖音、登录、支付、多图候选或15秒视频，除非它们被证明确实阻止核心验证。

### 第4周：复测、成本与商业判断

目标：判断是否值得进入正式MVP和服务端建设。

工作项：

- 邀请原用户再次创建一个新SKU或新版本。
- 回收实际发布证据和用户主观效果反馈。
- 统计每个发布内容包的生成、失败和重试成本。
- 访谈用户愿付方式：月订阅、额度包或两者组合。
- 评估内容是否带来互动/销售信号，但不做确定性归因结论。
- 输出 Android Motion Photo 的继续/停止决策；若已执行 Spike，再附目标设备兼容记录。
- 做Go/调整/停止评审。

周末输出：

- 四周验证报告。
- 功能取舍与下一版PRD。
- 正式后端与Credits方案。
- 产品命名候选与检索清单。
- 是否加入抖音和自动化数据闭环的决策。

## 4. 内测用户招募

### 4.1 进入条件

- 拥有至少一个自有SKU。
- 能提供3–6张合法可用的商品实物图。
- 正在或计划在小红书发布商品内容。
- 愿意在四周内至少完成两次创作。
- 愿意展示是否发布和发布结果。
- 接受AI可能产生商品失真并完成发布前审核。
- 使用 iPhone（iOS 17 或更高版本）参与本轮 App 内测。

### 4.2 排除条件

- 只想免费生成素材、不愿反馈或发布。
- 无法确认商品图、人物图和品牌素材使用权。
- 期望自动发布、保证爆款或保证销量。
- 主要推广违法违规、成人违规或明显高风险虚假宣传商品。
- 要求无限生成或共享他人的临时Key。

### 4.3 用户组合

建议3–5人覆盖：

- 3–5 名用户均使用 iPhone，至少覆盖两个 iOS 小版本或两种机型。
- 至少2种商品类型，避免只验证水杯。
- 至少1名已经稳定发布小红书内容的用户。
- 至少1名内容制作能力较弱的用户。

## 5. 内测说明

用户进入测试前应知道：

- Muses是未完成的内部Demo。
- 商品素材会发送到界面显示的指定生成服务。
- 生成内容可能改变商品，必须人工核对。
- 不保证内容通过小红书审核或提高销量。
- 当前 Demo 只提供 iPhone 版本；MP4 和静态图是 Live Photo 失败时的保底结果。
- 临时Key只限本人使用，不能转发。
- 额度有限，失败是否补偿由测试负责人判断。
- 本机项目可以删除，但已经发生的供应商调用和费用无法撤回。
- 用户应自行保存重要结果；Demo不提供云端备份。

## 6. 每次任务后的访谈

### 6.1 即时问题

1. 你最想跳过哪一步？为什么？
2. AI预填中哪些字段帮到了你，哪些字段反而麻烦？
3. 生成图最像真实商品的地方和最不真实的地方是什么？
4. AI动态是否让你更想发布？如果只给静态图，你是否仍会发布？
5. 你是否信任自己完成的审核？哪项最难判断？
6. 三个标题中是否有可直接使用的？正文改了多少？
7. 保存和去小红书发布之间还有什么手工工作？
8. 你最终发布了吗？如果没有，最大原因是什么？
9. 如果下周有另一个SKU，你会再次使用吗？
10. 若正式收费，你更愿意按月订阅还是按生成次数购买？

### 6.2 一周后回访

- 是否实际发布。
- 是否删除、重发或修改内容。
- 播放、点赞、收藏、评论和商品咨询的主观变化。
- 是否带来销售信号；明确标记为用户反馈，不称平台归因。
- 是否想再次生成同一SKU或新SKU。
- 最愿意付费保留的一个能力。

## 8. 成本与额度

### 8.1 总预算

- 四周总预算：100元。
- 达到80元时停止增加用户和SKU，先复盘。
- 达到100元时默认停止高成本生成，除非负责人明确追加预算。

### 8.2 用户配额

- 3–5名用户。
- 每人最多3个SKU。
- 每SKU默认1张图、1次AI动态。
- 单用户高成本任务并发为1。
- 不设置每日重置免费额度。
- 一人一Key，设置总额度、到期时间和模型范围。

### 8.3 失败补偿

建议规则：

- 供应商明确失败且扣费：人工补发一次。
- 客户端仅下载失败：不重新生成，重下结果。
- 用户审核不通过：是否重生成属于产品试验成本，需记录。
- 用户改变创意偏好：不视为技术失败。
- App重复提交导致重复扣费：计入产品缺陷成本并立即修复。

### 8.4 核心成本口径

`实际发布内容包成本 = 该内容包全部图片生成 + 动态生成 + 文本生成 + 失败重试的供应商成本`

Demo阶段本地转码、存储和开发人力可以单独记录，但不混入供应商推理成本。

## 9. Go / 调整 / 停止

### 9.1 Go：建设正式MVP和后端

满足多数条件：

- 至少2名用户实际发布。
- 至少2名用户7天内再次创作。
- 商品审核能有效发现主要失真问题。
- 单个发布内容包成本有合理订阅覆盖空间。
- 用户认为SKU事实复用和一体化流程比单独生图明显省事。
- iPhone 用户在必要时接受 MP4 降级，且不阻止核心内容发布。

下一步：

- 后端用户、Credits、任务编排和成本台账。
- 客户端不再使用供应商临时Key。
- 扩展稳定实况、提示词模板和小红书内容包。
- 重新评估正式命名。

### 9.2 调整：核心有价值但当前方案有阻力

典型信号：

- 用户喜欢图片但不需要AI动态。
- 用户发布静态内容，实况格式价值弱。
- AI预填纠错成本过高。
- 用户愿意发布但文案需要大量重写。
- iOS 实况价值弱，但 MP4 或静态图仍可接受。
- 用户只在少数视觉类商品中使用。

对应调整：

- 把高成本动态改为可选付费能力。
- 默认使用稳定实况而非视频模型。
- 收窄首发商品模板，而不必在入口禁止全部其他类目。
- 加强商品事实和文案模板，不急于增加平台。

### 9.3 停止或重新定位

- 用户只愿意免费生成，不实际发布。
- 大量生成结果改变商品，返工高于真实拍摄替代价值。
- 用户认为从SKU建档到审核比现有工具更麻烦。
- 单个被采用内容成本无法由合理价格覆盖。
- 产品价值完全依赖无法稳定实现的实况格式。
- 用户真正需要的是代运营服务，而不是自助工具。

## 10. 订阅方向（验证后）

参考Moras可以学习“双层变现”思想，但不直接复制价格或分佣：

- 自助版：订阅包含基础图片/动态Credits，超额购买。
- 专业版：更多SKU、品牌资产、稳定实况、模板和数据保留。
- 代运营/分佣：只有建立平台归因、结算、合同和服务能力后再评估。

首期不采用每日无限恢复额度。免费试用建议采用一次性成本封顶：

- 1个SKU。
- 1张图片。
- 1次低成本稳定实况或受限AI动态。
- 明确试用总成本，不通过日额度鼓励羊毛行为。

定价前必须先获得：

- 免费用户实际额度利用率。
- 被采用内容成本。
- 付费用户预期月生成量。
- 生成失败和返修率。
- 愿付价格访谈。

## 11. 平台路线

### MVP

- 只做小红书内容包、保存、复制和人工发布。
- 不把“打开小红书”记为已发布。

### 获得市场反馈后

- 先完善小红书结果回填和内容实验。
- 再适配抖音图片/视频比例、标题和话题。
- OAuth、自动发布、商品挂载和评论/订单同步分别做官方权限 Spike。
- 无官方权限时保持导出/系统分享，不使用Cookie托管、模拟登录、RPA或非公开接口。

## 12. Android兼容路线

四周只认证手头真实设备，不承诺全量覆盖。长期最小矩阵：

- 小米 HyperOS。
- OPPO ColorOS。
- vivo OriginOS。
- 三星 One UI。
- 华为 HarmonyOS 4.x。
- HarmonyOS NEXT 单独处理，不等同普通Android。
- iPhone作为发布与观看对照。

每台分别测试：

1. 本机相机原生动态照片。
2. Muses生成的GContainer Motion Photo。
3. 独立静态图和MP4。
4. 从iPhone导入的Live Photo。
5. 小红书内部选择和系统分享两个入口。

维护公开给内测用户的兼容清单，不用“理论支持”替代真机证据。
