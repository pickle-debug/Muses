# Muses 首轮开发任务与试用计划

日期：2026-09-11

依据：Q39—Q43 已确认的功能范围及 `04-三类素材与销售跟进功能逻辑.md`。

状态：开发任务拆分；本文件中的未完成项目不是已实现能力。应用工作区有其他持续开发的改动，实现前按最新代码核对并复用。

## 1. 本轮产品交付

用户从相册选取同一商品的几张图，得到可编辑商品草稿；在商品下手动选择静态图、Live 图、视频及数量，发起一批生成；审核和挑选素材后，自行到小红书发布，回填链接和实际数据；依据结果选择下一次创作方向。

首轮验收的终点：卖家可以独立完成“建商品→混合或单类生成→手动发布→回填→复盘→再生成”一次完整过程。

暂不投入：多商品相册自动分组、新建批量导入能力、小红书 OAuth/自动发布/自动读数、多镜头剪辑与配音、无人确认自动花费、统计自动判胜。仓库已有的文件批量导入功能保留，不因优先级降低而删除。

## 2. 开发任务

| 编号 | 交付 | 优先核对和复用的文件 | 验收结果 |
| --- | --- | --- | --- |
| T1 | 相册自动建一个 SKU 草稿 | `ProductInputView.swift`、`AppModel.swift`、`Models.swift`、事实识别接口 | 无手填编号/名称也可保存；识别预填可编辑；失败不丢图，不自动发起素材生成 |
| T2 | 三类生成选择与批次明细 | `Models.swift`、现有 Provider 模型和任务状态、`AppModel.swift` | 一批一个 SKU；各类型可选数量；只生成所选类型；目标候选与底层依赖任务分开计数 |
| T3 | 批量执行、结果库与重试 | 现有生成/审核页面、`SnapshotStore`、`AssetStore` | 部分失败保留成功结果；按子项重试；保存供应商任务 ID；重启不重复提交状态未知的任务 |
| T4 | 已选素材导出与手工发布登记 | `ResultViews.swift`、`PhotoLibraryService`、`LivePhotoService`、帖子跟进模型 | 只导出所选素材；保存成功不标成发布成功；实际帖子可使用多份素材，同一素材可用于多个帖子 |
| T5 | 指标快照与口径完善 | `PostMetrics`、`PostTracking`、`SalesFollowUpView.swift` | 缺失为空；累计不重复累加；明确统计时间、来源、退款与成本；SKU 销售不伪归因到帖子 |
| T6 | 描述性比较、建议与下一批次 | 商品详情、销售跟进、已有文本 Provider | 按实际数据比较；建议引用证据并说明缺口；采用建议预填生成表单，用户点击才生成 |

顺序建议：T1→T2/T3→T4→T5→T6。这是依赖顺序，不是要求新增六个独立模块。现有共享模型和持久化先兼容演进，避免重建整套后端。

### T1：降低建商品门槛

- 导入完成即保存一个草稿和内部唯一 ID，名称暂缺可用临时标题。
- 自动识别只预填可见/用户提供的事实；待确认字段可编辑，不凭图补造材质、容量或售价。
- 先保存后识别，识别失败不造成重复商品；用户编辑值不被迟到的识别结果静默覆盖。
- 分开“商品识别需要的图片数”和“某生成服务需要的图片数”，沿实际服务校验；不能把供应商当前限制当成所有建档流程的必需字段。

### T2/T3：批次可靠性先于高并发

- 用户选择类型与数量，看到费用估算及预计任务数后手动发起。费用未知显示未知/估算说明，不显示免费或 0。
- 首轮可从保守并发起步，按真实供应商配额调整；批量是一次提交多个工作项，不要求所有工作项同时执行。
- Live/视频可以复用同 SKU 的合格底图，目标类型和输出分别记录。选择静态不会调用视频生成。
- 首版视频沿用当前单镜头图生视频能力，Live 以轻动态及配对封装交付；更复杂视频不作未实现的承诺。
- 持久化每个工作项的状态、输入快照、资产、失败原因与已知费用。不要靠一个全局当前任务变量承载多个异步任务。
- 任务状态未知时先核查，不自动新建收费任务；取消停止未提交项，对已提交项按供应商真实能力处理。

### T4/T5：素材、帖子、交易不要混在一起

- 导出所选素材，复制文案并打开小红书，由商户完成发布；返回后粘贴链接，登记实际素材类型与时间。
- 手机相册导出成功不代表 Live 在小红书发布后仍保留动态，真机试用必须检查最终内容。
- 一篇笔记使用多张图时仅记录一份帖子指标，不把整篇订单复制到每张素材再求和。
- 回填以累计快照为首版简化口径，保留更新时间。缺失字段可空着，不强迫用户编造订单。
- 数值比较由确定性计算完成；明确分母、来源和观察窗口。AI 负责解释和建议，不能凭空算出缺失的归因交易。
- 老数据迁移时保留原始值与历史来源未知标记，不能把旧版默认 0 当作已证实零成交。

### T6：建议必须能用于下一次制作

输出包含：观察到的事实、尚不能判断的部分、建议调整的一个主要变量、对应素材/帖子证据。

用户点击采用后，保留本次建议与旧版本关联，预填下一批次的素材类型、场景或卖点；仍由用户决定数量并提交。

没有新数据时可说明缺口或提出新的探索方向，不声称已经“学到购买偏好”。自然流量下多几单是观察，不自动升级为因果或统计显著结论。

## 3. 验证方式

实现时在现有检查路径中增加必要用例，避免新增测试框架。每个共享状态或数据修改先验证旧记录可读取。

- T1：未填名称可存草稿；识别失败/迟到；编辑后重开；同次导入重复操作。
- T2/T3：只静态、只 Live、只视频及混合；子项失败；重启恢复；未知提交不重复收费；成功数按目标候选统计。
- T4：相册拒绝/恢复授权、单项保存失败、不同类型分别导出；一帖多素材、同素材多帖、重复链接登记。
- T5：缺失与真实 0、同帖多个累计快照、退款补录、不同窗口不能直接比较、无订单归因不显示虚假购买转化率。
- T6：有数据时引用事实，无数据时保留结论；采用建议不立即触发付费生成。

代码构建和状态测试通过后，还需用有效模型配置与真实 iPhone 验证生成、Live 封装、相册保存及小红书最终发布。预览模式不作为真实素材或销售效果的验收证据。

## 4. 试用与市场验证同步推进

### 第一位卖杯子用户与妻子

由用户本人和妻子协调，不由助手擅自发消息。记录一个完整真实任务：原始商品图、最终目标、生成候选、弃用原因、人工改动、实际发布以及后续数据。

软件任务和市场任务相互提供证据：

| 开发进展 | 妻子/朋友提供的现场反馈 |
| --- | --- |
| 建档和批次可用 | 是否能独立建商品；最常改哪些字段；实际选择哪种类型和数量 |
| 审核和导出可用 | 哪些素材不能用；返工原因；最终发布了什么；Live 是否真实可发布 |
| 数据回填可用 | 后台实际有哪些字段；愿不愿意持续回填；一次耗时多久；订单来源是否清楚 |
| 复盘建议可用 | 是否理解/采纳；是否用于下一批；有没有比直接再生一批更有帮助 |

用户每周查看至少一段完整任务证据，与妻子选本周最重要的问题；不要求用户承担日常卖货，也不只凭二手功能愿望安排开发。

### 第二阶段的外部验证建议

首个用户走通后，建议从现有人脉中再找 2—3 位有相似内容生产需求的卖家试用。这是小规模检验建议，不是统计充分性或已同意的外部邀约。

重点观察是否在没有朋友帮忙、没有免费人工代做的情况下重复使用。询问当前替代方法的成本和实际付款意愿；正式定价依据真实生成/支持成本及付费访谈确定，不在本计划中编造价格。

## 5. 如何判断继续开发什么

- 生成多、采用少：先定位失真/审美/场景/格式问题，不能用更大批量掩盖。
- 采用多、发布少：优先处理导出和发布准备，不急着加模型。
- 发布多、数据少：先减少回填成本，并确认商家实际可得数据；不要先造复杂分析。
- 持续使用但不愿付费：检查客户选择、替代成本、定价及真实价值，不能默认还缺更多功能。
- Live 效果一般、静态持续被采用：允许静态成为主要价值，保留三类选择；单个格式未胜出不等于整项软件失败。
- 商品销售改善：记录条件和费用，仍单独检验商家是否持续为软件付款。

两周可以作为第一轮试用观察的时间盒，具体开发排期按实际代码差距和在职时间评估；不承诺两周内完成全部功能或得出销量因果结论。
